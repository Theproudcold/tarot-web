# 内容质量优化闭环设计

## 背景

当前项目已经具备三层内容生成能力：

1. `server/ai/agents/*.js` 已经对多 Agent 提示词加入了“可替换性测试”、反套话约束、few-shot 对照和阶段分工。
2. `src/lib/readingContract.js` 已经能在 AI 输出过于空泛时回退到本地牌阵驱动文案。
3. `src/lib/tarotReading.js` 已经提供了较稳定的本地 `quote / mantra / followUps` 生成能力。

这说明项目已经不是“能不能生成内容”的问题，而是“内容质量能不能稳定提升且可验证”的问题。

## 现阶段核心问题

### 1. 缺少稳定评测基线

现在的测试主要验证：

- prompt 是否包含关键约束
- 某些模板句是否会被 fallback 拦住

但还没有一套固定牌阵与问题样本，去持续判断：

- 这次改动是否真的减少了套话
- 叙事是否更连贯
- advice 是否更可执行
- 不同问题类型下是否出现风格塌陷

### 2. few-shot 资产偏少

`server/ai/agents/fewShotExamples.js` 目前主要提供一组“坏 vs 好”的示例和一段单牌风格样本。这个量级只能起到“别太烂”的约束，撑不起更细的风格控制。

### 3. fallback 规则仍偏粗

`src/lib/readingContract.js` 当前主要依赖：

- 模板句黑名单
- 是否命中牌名 / 主导元素锚点

这种策略能挡住明显套话，但对“看起来挺文艺、其实可替换”的句子识别还不够稳。

### 4. 缺少统一内容标准文档

当前“什么叫好内容”散落在 prompt、测试、few-shot 例子和代码逻辑里，没有一份统一的内容策略文档来约束后续优化方向。

## 目标

本轮优化目标不是继续无节制地堆 prompt，而是建立一个可持续的内容质量闭环：

1. 先建立固定评测样本和验收标准。
2. 再基于评测结果迭代 prompt 与 fallback。
3. 最后把结果沉淀成文档与前端感知优化。

## 非目标

本轮不优先处理以下事项：

- 新增全新功能模块
- 重做 UI 结构
- 引入外部复杂评测平台
- 追求“模型绝对最优输出”

本轮重点是让现有系统的内容质量优化从“凭感觉”升级为“可观察、可回归、可沉淀”。

## 候选方案

### 方案 A：先做内容评测基线

做法：

- 固定一组牌阵 + 问题输入样本
- 定义质量维度和打分标准
- 建立本地评测脚本和最小回归报告

优点：

- 能把后续优化变成有证据的改动
- 能防止 prompt 改一轮、质量波动一轮
- 能帮助发现不同场景下的薄弱点

缺点：

- 前期见效不如直接改 prompt 那么“热闹”
- 需要先做一轮样本整理

### 方案 B：直接继续强化 prompt 与 few-shot

做法：

- 扩写 few-shot
- 增加更多禁止项和风格约束
- 继续细化多 Agent 提示词

优点：

- 上手快
- 对局部文案质量可能立刻有改善

缺点：

- 无法稳定判断是否真的提升
- 容易进入“越改越重、越重越玄”的状态

### 方案 C：先做前端感知优化

做法：

- 优化阶段文案
- 强化“本次解读为什么更具体”的展示
- 把流程感做得更顺滑

优点：

- 用户主观体验会立刻改善
- 对展示层提升明显

缺点：

- 不能解决底层内容质量不稳的问题
- 容易把包装做得比内容本身更努力

## 结论

选择 **方案 A 为主线**，执行顺序为：

1. 评测基线
2. prompt / few-shot / fallback 联动优化
3. 文档沉淀
4. 前端感知打磨

这条路最土，但最靠谱。先把尺子做出来，再谈怎么把东西磨好。

## 详细设计

### 一、建立内容评测样本集

新增一组固定样本，至少覆盖以下场景：

- 关系推进类问题
- 事业 / 决策类问题
- 情绪迷茫但没有明确问题
- 高张力冲突牌阵
- 元素极端偏科牌阵
- 用户问题非常空泛
- 用户问题非常具体

每个样本包含：

- 3 张牌及正逆位
- 语言
- question
- 期望关注点
- 应避免的套话类型

### 二、定义质量验收维度

对 `summary / perCard / advice / quote / mantra / followUps` 定义最小验收标准：

- **牌面锚定度**：是否能看出与这次牌阵有关
- **叙事连贯性**：过去 / 现在 / 未来是否形成同一条线
- **行动可执行性**：建议是否能落到当下动作
- **非模板化程度**：是否能通过“可替换性测试”
- **语气稳定性**：避免宿命论、空泛鸡汤、机械堆叠术语

### 三、扩展 prompt 资产而非盲目加长 prompt

不是无限往 `instructions` 里塞字，而是把 few-shot 资产分层：

- 关系类
- 决策类
- 低信息输入类
- 高情绪张力类

同时给 `quote / mantra / followUps` 建立 2-3 套风格变体，防止所有输出都像一个老师傅在同一家店里反复念稿。

### 四、增强 fallback / merge 判定

优化 `src/lib/readingContract.js` 的策略：

- 从“黑名单模板句检测”升级到“模板句 + 弱锚定 + 低信息密度”的联合判断
- 保留文艺但仍具独特性的表达
- 对 `followUps` 单独做层级和差异度判断，防止两个问题只是换个说法重复一遍

### 五、补齐调试与观察能力

继续利用 `server/ai/debugMicrocopy.js`，但把它从“打印替换前后快照”升级到：

- 标记哪些字段触发了 fallback
- 标记触发原因
- 支持对单个样本跑完整流程后输出可读报告

### 六、文档化内容标准

把“高质量塔罗解读内容”的标准写成开发文档，而不是只藏在 prompt 里。后续改动要优先对齐文档，再改代码。

## 风险与应对

### 风险 1：评测样本写得太理想化

应对：

- 样本既要有理想输入，也要有真实世界的烂输入

### 风险 2：few-shot 越堆越重

应对：

- 先分场景，再决定是否注入，不追求所有样本全塞

### 风险 3：fallback 过强，吞掉了有灵气的 AI 文案

应对：

- 保留“文学性但独特”的白名单判断思路
- 为保留案例补测试

### 风险 4：前端展示先跑太快

应对：

- 在评测基线和底层优化完成前，不把展示层当成主战场

## 分阶段里程碑

### Phase 1：评测基线落地

- 固定样本集
- 固定维度
- 固定本地评测脚本

### Phase 2：内容生成资产升级

- 扩展 few-shot
- 优化 Agent 提示词组织
- 调整 fallback 合并逻辑

### Phase 3：可观察性和文档沉淀

- 输出调试报告
- 补内容策略文档
- 在 README 或专项文档中说明验证方式

### Phase 4：前端感知打磨

- 优化运行态文案
- 优化完成态文案收束
- 强化“内容更具体”的感知证据

## 完成标准

当以下条件同时满足时，视为本轮方案达标：

1. 存在可重复执行的固定样本评测集。
2. 改 prompt / fallback 后能看到前后对比结果。
3. `quote / mantra / followUps` 的模板化问题明显下降。
4. 文档中明确了内容质量标准与后续演进路径。
